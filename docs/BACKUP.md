# DB 백업과 복구

이 시스템의 **모든 것**이 `server/db/database.db` 파일 하나에 있습니다 — 예약, 자동방송 시각,
볼륨, API 키, 방송 이력, 아침 안내문 설정까지 전부입니다. 이 파일이 깨지면(디스크 불량,
정전 중 쓰기, 실수로 삭제) 되돌릴 방법이 이 백업뿐입니다.

> Claude Code의 checkpoint나 `/rewind`는 **DB 변경을 되돌리지 못합니다.** 코드만 되돌립니다.

## 자동으로 되는 것

`server/services/backup.js`가 합니다.

| | |
|---|---|
| 언제 | 서버 기동 5초 뒤 1회 + 매일 04:30 |
| 어디에 | `server/db/backups/carecast_YYYYMMDD_HHMM.db` |
| 얼마나 | 30일 보관, 그보다 오래된 것은 자동 삭제 |
| 시각 변경 | 관리자 화면 **시스템 설정 → 방송 운영 · 자동화 → 방송 알림 · 백업**(2026-09-23부터. 값은 `settings` 표의 `backup_time`). 저장하면 서버를 다시 켜지 않아도 새 시각으로 예약된다. 오래된 기록 정리(`retention_time`, 기본 04:35)는 이 시각을 따라가지 않는다 — 「백업 직후 정리」 순서를 지키려면 백업 시각을 정리 시각보다 앞에 둔다 |

**기동 시에도 한 번 하는 이유**: 현장 PC는 자동 종료·재시작을 쓰기 때문에, 04:30에 PC가 꺼져
있으면 그날 백업이 통째로 없습니다. 기동 때 한 번 뜨면 최소 하루 한 벌은 남습니다.

**파일 복사가 아니라 `VACUUM INTO`를 씁니다.** 이 DB는 WAL 모드라서 `.db` 파일만 그냥 복사하면
`-wal`에 있던 최신 내용이 빠진 **반쪽짜리 스냅샷**이 나옵니다. `VACUUM INTO`는 SQLite가 직접
일관된 스냅샷을 새 파일로 씁니다.

**만든 백업은 곧바로 다시 열어 확인합니다.** 표 개수를 세고 `settings`·`schedules`·`broadcasts`를
실제로 읽어봅니다. 실패하면 그 파일을 지우고 화면에 경보를 띄웁니다 — 깨진 백업을 30일치
모아두면 백업이 없는 것보다 나쁩니다. "있다"고 믿게 되니까요.

## 복구하는 법

1. **서버를 먼저 끕니다.** 켜진 채로 파일을 바꾸면 안 됩니다.
   - 작업 표시줄의 CareCast 창을 닫거나, 작업 관리자에서 `node.exe` 종료
2. 지금 파일을 **지우지 말고 이름만 바꿔 둡니다.** (복구가 잘못됐을 때 돌아올 자리)
   ```
   server\db\database.db  →  database.db.깨짐-20260830
   ```
   `database.db-wal`, `database.db-shm`이 있으면 그것도 같이 옮깁니다.
3. `server\db\backups\` 에서 **가장 최근 파일**을 골라 `server\db\database.db` 로 복사합니다.
   (이름을 `database.db`로 바꿔야 합니다)
4. 서버를 다시 켭니다. 바탕화면 `CareCast 시작.bat`
5. 관리자 화면에서 **예약 목록**과 **시스템 설정**이 제대로 보이는지 확인합니다.

되돌리고 싶으면 2번에서 옮겨둔 파일을 다시 `database.db`로 되돌리면 됩니다.

## 외부 매체 복사 (권장)

위 백업은 **같은 디스크 안에** 있습니다. 디스크 자체가 죽으면 백업도 같이 죽습니다.
한 달에 한 번 정도 USB나 다른 PC로 옮겨 두시면 좋습니다.

```
server\db\backups\ 폴더에서 최근 파일 1~2개를 USB로 복사
```

자동화는 하지 않았습니다 — USB가 꽂혀 있지 않을 때 조용히 실패하면 "백업되고 있다"는 착각만
남습니다. 사람이 하는 편이 낫습니다.

## 복구 리허설 결과 (2026-08-30)

실제로 해봤습니다. 백업 파일을 다른 경로에 복구해서 운영 DB와 대조했습니다.

```
백업 파일: carecast_20260830_1317.db (112KB)
표 21개 대조 — 행 수가 다른 표: 0개
설정 표본 : morning_time = 07:50
예약 건수 : 0
이력 건수 : 13
→ 복구 리허설 통과
```

이 리허설에서 **제품 결함도 하나 찾았습니다.** 검증 함수가 DB 핸들을 `try` 안에서만 닫고
있어서, 검증이 실패하면 핸들이 열린 채 남았습니다. 그 상태로 깨진 백업을 지우려 하면
Windows에서 `EBUSY`로 실패해서, 지우려던 깨진 파일이 그대로 쌓입니다. `finally`로 옮겨
고쳤고 `backup.test.js`가 고정합니다.

## 언제 사람이 직접 백업해야 하나

- **DB 구조를 바꾸기 전**. 마이그레이션은 자동 백업 주기를 안 기다립니다.
- 큰 설정 변경 전 (자동방송 순서 전면 재편 등)

이때는 서버를 끄고 `server\db\database.db`를 복사해 두면 됩니다.
