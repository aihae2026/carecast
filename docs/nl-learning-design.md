# 자연어 예약 누적 학습 — 설계 (고도화 제안 #10, 2026-09-03)

> **공개판 안내:** 2026-09 시점 설계 기록입니다. 공개판에 없는 내부 문서(CLAUDE.md 등)를 가리키는 곳이 있습니다.

사용자 요청: "자연어로 하면 할수록 DB가 쌓여서 그걸 바탕으로 판단·규칙을 내리는 것."
등록: 고도화 제안 #10(추천). **이 문서는 계획이고, 구현은 승인 후다**(CLAUDE.md 게이트 1).

## 1. 실측 — 지금 무엇이 쌓이고 무엇이 안 쌓이나

| 무엇 | 어디에 | 쌓이나 |
|---|---|---|
| 사람이 쓴 원문 (AI 경로) | `schedule_drafts.raw_input` | ✅ 쌓인다 |
| AI가 읽어낸 값 | 같은 행의 title·content·scheduled_time·broadcast_type·볼륨 | ✅ 쌓인다 |
| 승인/거절 여부 | `status`(approved·rejected) + `resolved_at` | ✅ 쌓인다 |
| **사람이 승인하며 고친 값** | **어디에도 없다** | ❌ |
| **초안 ↔ 최종 예약 연결** | **없다** | ❌ |
| 사람이 쓴 원문 (규칙 파서 경로) | 없다 — `parse-phrase`는 파싱해 모달만 채운다 | ❌ |

**핵심 결함**: `approveDraft(id, overrides)`의 `overrides`가 곧 "사람이 고친 것"인데
(routes/scheduleDrafts.js:121), 이 값은 `insertSchedule`로 흘러가고 **버려진다**.
만들어진 `scheduleId`도 초안 행에 안 적힌다(:144). 그래서 나중에 초안과 최종 예약을
맞대어 "무엇을 고쳤나"를 계산할 길이 **원천적으로 없다.**

→ **이 문서의 1단계는 학습이 아니라 "재료 모으기"다.** 지금 상태로는 어떤 학습도 못 한다.

거절(rejected)도 마찬가지다. 왜 거절했는지가 없으면 "이 표현을 잘못 읽었다"인지
"마음이 바뀌었다"인지 구분이 안 되므로, 거절은 학습 재료에서 **뺀다**(1단계 기준).

## 2. 단계 계획

### 1단계 — 재료를 남긴다 ✅ **끝남 (2026-09-03, 사용자 승인 "1단계 ㄱ")**

마이그레이션 `0017_add_schedule_drafts_learning.sql` + `schema.expected.json` + `verify:db`
PASS(3종 세트). `approveDraft`가 승인 시점에 `schedule_id`·`approved_json`·`edited_fields`
셋을 채운다. 가드 `server/test/nl-learning-record.test.js` 여섯.

**구현하며 정한 것 둘**(설계에 없던 판단):
- **값이 같으면 수정으로 세지 않는다.** 승인 모달은 필드를 채운 채 열려서 화면이 안 고친
  값을 그대로 되보낸다 — 그것까지 세면 수정률이 통째로 부풀려져 통계가 거짓말을 한다.
- **`null`·`undefined`·`''`는 같게 본다**("안 정해짐"). 빈 값의 표현 차이만으로 수정이
  되면 안 된다.

아래는 원래 계획(근거로 남긴다).

`schedule_drafts`에 컬럼 셋:

| 컬럼 | 뜻 | 왜 |
|---|---|---|
| `schedule_id` | 승인으로 만들어진 예약 행 id | 초안↔최종을 잇는 유일한 끈 |
| `approved_json` | 승인 시점의 최종값 스냅샷(JSON) | 예약이 나중에 수정·삭제돼도 "그때 무엇으로 확정했나"가 남는다 |
| `edited_fields` | 사람이 고친 필드 이름 목록(JSON 배열) | 계산 결과를 미리 굳혀 둔다 — 나중에 세는 쪽이 스키마 변화에 안 흔들린다 |

- 마이그레이션 `db/migrations/0017_add_schedule_drafts_learning.sql` +
  `db/schema.expected.json` 갱신 + `npm run verify:db` (CLAUDE.md 규칙 4의 3종 세트).
- 기존 행은 전부 NULL — **NULL은 "몰라서 비어 있음"이지 "안 고쳤음"이 아니다.**
  집계에서 반드시 제외한다(2단계의 규칙).
- 규칙 파서(`parse-phrase`) 경로는 **1단계에서 건드리지 않는다.** 그 경로는 초안을 안
  만드는 것이 설계(즉시 모달)라, 기록을 붙이려면 그 설계를 바꿔야 한다 — 범위를 키운다.

**남기지 않는 것**: 개인정보. `raw_input`은 이미 민감정보 검사를 통과한 문장이지만,
집계 결과에 원문을 그대로 노출하지 않는다(3단계 화면 규칙).

### 2단계 — 세어서 보여주기만 한다 ✅ **끝남 (2026-09-03, 사용자 결정 "새 탭")**

`server/domain/nlStats.js`(집계·표본 정의) + `server/routes/nlStats.js`(GET /api/dev/nl-stats,
읽기 전용) + 「고도화 제안 > **자연어 학습**」 탭(`src/components/admin/sections/NlLearningCard.jsx`).
가드 `server/test/nl-stats.test.js` 여덟(뮤테이션 넷으로 RED 확인). DB 변경 없음.

**구현하며 정한 것 여섯**(설계에 없던 판단):
- **표본 = `status='approved'` 이면서 `edited_fields IS NOT NULL`.** 정의를 도메인 모듈 한 곳에
  (질의문까지 함께) 두었다 — 라우터가 따로 고르면 정의가 두 벌이 된다.
- **`isKnownWord()`는 `domain/ontology.js`에 두었다.** "사전에 없는 낱말"을 세려면 사전을 봐야
  하는데, 판정을 통계 쪽에 두면 사전이 두 벌이 된다(규칙 파서·AI 파서가 같은 사전을 봐야
  한다는 규율이 곧바로 깨진다). 사전이 거기 있으니 "사전에 있나"도 거기서 답한다.
- **낱말은 문장당 한 번만, 두 번 이상 나온 것만.** 한 문장에서 세 번 말한 것이 3건이 되면
  빈도가 사람 수가 아니라 말버릇을 잰다. 한 번짜리는 방송 주제 낱말로 목록을 덮는다.
- **불용어 목록을 따로 뒀다**(시각·날짜·요청 표현). 파서는 이것들을 낱말 사전이 아니라
  숫자·규칙으로 읽어서 ontology에 없다 — 안 거르면 상위 목록이 '내일'·'예약'뿐이다.
- **낱말마다 `withTypeEdit`(그 낱말이 든 문장에서 유형까지 고친 횟수)를 함께 센다.** 빈도만으론
  동의어 후보와 방송 주제 낱말이 구분되지 않는다. 3단계 임계값은 이 둘을 함께 봐야 한다.
- **오전/오후 오독 = 분은 같고 시만 정확히 12시간 어긋난 수정**(시각을 고친 건에 한해).

**가짜 표본 26건으로 화면을 본 뒤 고친 것 셋**(2026-09-03, 사용자 결정):
- **서술어로 끝나는 토막은 후보에서 뺀다**((나)안). 어미를 잘라 명사를 복원하려 들면 목록이
  끝없이 늘고 자르다 명사가 깨진다 — 그래서 통째로 버린다. `줘·요·다·다고`는 길이 무관,
  `고·게·서·며·지·려`는 세 글자부터(광고·편지·문서·격려 같은 두 글자 명사를 지킨다).
  **대가**: `신청서`처럼 세 글자 이상 명사도 함께 빠진다 — 후보 하나 덜 보이는 손해로 받는다.
  덤으로 복수 접미사 `들`을 조사와 함께 떼고(어르신/어르신들이 갈리지 않게), 한글로 쓴 시각
  (`두시`·`열한시`)과 수사(`하나`)를 불용어에 넣었다.
- **낱말 목록을 '유형도 고침'順으로 세운다.** 빈도만으로 줄 세우면 그냥 자주 말하는 방송 주제
  (`건강강좌`)가 목록을 덮고, 정작 사전에 넣을 값어치가 있는 말이 아래로 밀린다.
- **표본은 최근 창(`nl_stats_window`, 기본 50건)만 본다.** 최근 것이 지금의 말버릇이다.
  **주의**: 창 밖으로 나간 표본은 집계에서 사라진다 — "한 번 본 것"을 기억하려면 3단계가
  제안 행으로 굳혀야 한다(제안 표는 남는다). 지금은 굳히는 곳이 없다.

**가짜 표본으로 배운 것과 안 배운 것.** 표본은 세션이 만든 것이라, 거기서 나온 "유형 오독"을
사전에 그대로 넣지 않았다 — 실제 파서에 돌려 보니 `티비로 영상 틀어줘`는 이미 후보 둘을 두고
되묻는 설계된 동작이었고(CLAUDE.md), 진짜 사전 구멍은 `종`(단독, `종소리`만 있음) 하나뿐이었다.
그것도 넣지 않았다 — 한 글자는 `종례`·`종일` 같은 말에 걸려 안내 방송이 차임벨로 바뀔 위험이
사전 한 줄로는 안 막힌다. **현장 문장이 쌓인 뒤에 판단한다.**

아래는 원래 계획(근거로 남긴다).

#### 원안

`GET /api/dev/nl-stats` — 관리자 화면 "고도화 제안" 옆 카드 하나.

| 지표 | 계산 | 무엇에 쓰나 |
|---|---|---|
| 표현별 빈도 | `raw_input`에서 어휘 사전(ontology)에 **없는** 낱말 상위 N | 동의어 후보 |
| 필드별 수정률 | `edited_fields` 집계 (분모: 컬럼이 채워진 승인 건만) | 어디를 자꾸 고치나 |
| 오전/오후 오독률 | `scheduled_time`이 ±12시간으로 바뀐 비율 | 확인 카드 기본값 조정 근거 |
| 유형 오독 | `broadcast_type`이 바뀐 짝(예: video→youtube-tv) | 되묻기 문구 개선 |

**표본이 적으면 아무 말도 안 한다.** 최소 건수(기본 20, 설정 `nl_stats_min_samples`)
미만이면 "아직 판단할 만큼 안 쌓였습니다"만 띄운다 — 서너 건으로 규칙을 만들면
그게 곧 오작동이다.

### 3단계 — 제안만 한다 (자동 반영 없음)

2단계 통계가 임계를 넘으면 **고도화 제안 행을 자동 생성**한다(status: 추천).
예: "'티비로'라는 표현이 12번 나왔고 그중 10번을 사람이 youtube-tv로 고쳤습니다.
ontology의 youtube-tv 동의어에 추가할까요?"

- **어휘 추가는 사람이 승인한 뒤 코드(ontology.js)에 손으로 반영한다.** DB에서 사전을
  덮어쓰는 길은 만들지 않는다 — 규칙 파서와 AI 파서가 같은 사전을 봐야 하고
  (CLAUDE.md), 그 단일 출처가 코드에 있는 것이 이 저장소의 규율이다.
- 제안은 **초안 → 승인** 패턴 그대로다(CLAUDE.md AI 결과물 규칙). 학습 결과가 방송
  동작을 조용히 바꾸는 일은 없다.

## 3. 하지 않을 것 (경계를 먼저 못 박는다)

- **자동 학습 반영**: 통계가 사전·기본값을 자동으로 바꾸지 않는다. 요양원 방송은
  조용한 오작동이 가장 찾기 어려운 실패다.
- **모델 파인튜닝·임베딩**: 이 규모(하루 몇 건)에서 값어치가 없다. 세는 것으로 충분하다.
- **원문 노출**: 집계 화면에 `raw_input` 전문을 띄우지 않는다(낱말·패턴만).
- **거절 사유 추론**: 거절 이유를 모델에게 물어 채우지 않는다. 모르는 것은 모르는 채로.
