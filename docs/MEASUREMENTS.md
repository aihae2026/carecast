# 성과 측정 — 빈 양식과 작성 예시

> **지금부터 모은다.** 제출 직전에 몰아서 쓰면 기억으로 쓰게 되고, 기억은 좋은 쪽으로
> 기운다. 한 건이라도 **실제로 잰 것**이 추정 열 건보다 낫다.
>
> **규칙 셋**
> 1. **기존 로그를 먼저 쓴다.** 수치를 만들려고 새 로그나 개인정보를 더하지 않는다.
> 2. **잰 것과 물어본 것과 짐작한 것을 섞지 않는다.** 칸이 따로 있다.
> 3. **직원 발언은 실제 인용 + 사용 동의**가 있을 때만. 인터뷰를 지어내지 않는다.

---

## 1. 빈 양식 — 업무 하나에 표 하나

같은 업무를 여러 번 재면 **행만 늘린다.** 표를 새로 만들지 않는다.

```
### 업무: ____________________________

| 칸 | 값 | 적는 법 |
|---|---|---|
| 측정자 | ____ | **익명 ID 만**(예: 직원A). 이름·직책을 적지 않는다 |
| 기간 | ____ ~ ____ | 며칠치를 합친 것인지 |
| 같은 조건인가 | ____ | 이전과 이후가 **같은 일**인지. 다르면 무엇이 다른지 한 줄 |
| 시작 기준 | ____ | "무엇을 하는 순간부터" 를 문장으로. 애매하면 이 숫자는 못 쓴다 |
| 종료 기준 | ____ | "무엇이 되면 끝인지" |
| 이전 1회 시간 | ____ 분 | 도입 전 |
| 이후 1회 시간 | ____ 분 | 도입 후 |
| 실제 수행 건수 | ____ 회 | **기간 안에 진짜로 한 횟수.** 예상 횟수가 아니다 |
| 실패·재시도 | ____ 회 | 0 이면 0 이라고 적는다. 비워 두지 않는다 |
| 근거 | ____ | 로그 이름·화면·기록지 등 **다시 찾아볼 수 있는 것** |
| 잰 것인가 물어본 것인가 | 측정 / 진술 / 추정 | 섞지 않는다 |
```

**계산은 이 표에서 하지 않는다.** 절감 시간 같은 값은 제출 문서에서 한 번만 계산하고,
그때 **어느 표의 어느 행에서 나왔는지**를 함께 적는다.

## 2. 작성 예시 — **더미다. 실제 값이 아니다**

> ⚠️ **아래는 전부 더미(가짜) 값이다.** 양식을 어떻게 채우는지만 보여 준다.
> **이 숫자를 제출 문서나 발표에 옮겨 쓰지 않는다.** 실제 측정이 들어오면 이 절은 지운다.

### 업무: 점심 식사 전 안내 방송 내보내기 〔더미〕

| 칸 | 값 〔더미〕 | |
|---|---|---|
| 측정자 | 직원A | 익명 ID |
| 기간 | 2026-09-01 ~ 2026-09-12 | 평일 10일 |
| 같은 조건인가 | 같음 | 같은 시간대·같은 안내문 |
| 시작 기준 | 방송실에 들어가 기기 전원을 켜는 순간 | |
| 종료 기준 | 안내가 끝나고 마이크를 내려놓는 순간 | |
| 이전 1회 시간 | 6 분 〔더미〕 | |
| 이후 1회 시간 | 0 분 〔더미〕 | 자동 발사라 사람이 개입하지 않음 |
| 실제 수행 건수 | 10 회 〔더미〕 | 평일만 |
| 실패·재시도 | 1 회 〔더미〕 | 09-05 인터넷 끊김으로 1회 수동 |
| 근거 | `broadcasts` 표의 그 기간 행 〔더미〕 | 다시 조회 가능 |
| 잰 것인가 | 측정 | 로그에서 셈 |

**이 표에서 바로 읽히는 것 〔더미〕**: 10회 중 9회가 사람 손을 안 거쳤다.
**이 표에서 안 읽히는 것**: 그 9회가 **제 시각에** 나갔는지는 이 표가 모른다 —
그건 정시성 관측이 따로 본다(`PROJECT_PROFILE.md` §6-2, 합격선 4.0초).

그 뒤는 비어 있다. **없는 기간을 추정으로 메우지 않는다.**

## 3. 실제로 잰 것 ① — 현장 방송 이력 (2026-09-14 집계)

> **기존 로그만 썼다.** 새 로그도, 개인정보도 더하지 않았다(§0 규칙 1).
> **방송 문안은 한 줄도 읽지 않았다** — 건수·날짜·성공 칸만 셌다.

| 칸 | 값 |
|---|---|
| 자료 | 현장 PC 데이터베이스 **사본**(`docs/audit/sandbox/site.db`, 2026-09-06 확보) |
| 기간 | **2026-07-20 ~ 2026-09-01**, 날짜가 붙은 **44일** |
| 대상 | `broadcasts` 표 — 날짜가 있는 **490건** |
| 측정자 | 자동(시스템이 남긴 기록을 집계) |

### 나온 값

| 무엇 | 값 |
|---|---|
| **자동 일과방송 5종** | 209건 · **44일 중 38일(86%)에 다섯 건이 모두** 기록됨 |
| 나머지 6일 | 2건 2일 · 3건 1일 · 4건 3일 |
| **반복 예약**(환기 안내 3쌍) | 255건 · **44일 중 40일(91%)에 여섯 건이 모두** 기록됨 |
| **수시 안내(TTS)** | 26건 — 44일에 26회, 하루 평균 0.6회 |
| 기록상 성공률 | 세 갈래 모두 **100%**(실패로 적힌 건 0) |

### 이 숫자를 어떻게 읽어야 하나 — **세 가지를 분명히 한다**

**① 「성공 100%」를 「다 들렸다」로 읽으면 안 된다.** 이 값은 **기록상** 성공이다.
2026-09-14 저녁에 **기록은 성공인데 소리는 안 난** 방송이 실제로 있었다(저녁기도).
당시 시스템은 그것을 잡지 못했다. **그래서 고쳤다** — 소리 낼 화면이 없으면 성공으로
적지 않고 경보를 올린다. 즉 **이 표의 100%는 「그때의 기록이 그랬다」까지만 참이다.**

**② 5건이 안 되는 6일의 원인은 이 사본으로 못 가른다.** PC가 꺼져 있었는지, 그 방송을
꺼 뒀는지, 진짜로 빠졌는지를 건수만으로는 구별할 수 없다. **「누락 6일」이라고 적지 않는다.**
가르려면 그날의 가동 기록(`server_boot`)과 설정 이력이 필요하다. `[미확인]`

**③ 날짜가 없는 행이 277건 더 있다.** 옛 기록이라 날짜 칸이 비어 있어 **어느 날 것인지
붙일 수 없다.** 위 집계에서 통째로 뺐다 — 넣으면 하루 189건 같은 값이 나와 평균이 망가진다.

### 아직 못 잰 것

| 무엇 | 왜 |
|---|---|
| **방송 지연**(예정 시각 → 첫 소리) | 이 사본에는 `delay_ms` 가 **0건** 기록돼 있다. 그 칸은 나중에 생겼다. **지금 현장 사본을 새로 받으면 잴 수 있다** |
| **도입 전/후 비교** | 도입 전 기록이 없다. 이 시스템이 생기기 전에는 **아무 기록도 안 남았다** — 그게 처음 문제 ②였다 |
| **직원 업무 시간 절감** | 사람이 재야 한다. §1 양식으로 모은다 |

> **도입 전 수치가 없다는 것 자체가 근거다.** 비교할 숫자가 없는 이유는 「안 쟀다」가 아니라
> **「잴 방법이 없었다」** 이기 때문이다. 지금은 하루 11~12건이 자동으로 남는다.

**현장 사본이 맞는지 확인했다**: `schedules` 의 환기방송 6건(09:10·09:20 / 12:00·12:10 /
17:00·17:10)이 `PROJECT_PROFILE` §6-1 의 현장 값과 일치한다. `[구현]`

|---|---|---|
| 예약(환기 안내) | 333 | 0 |

**경보를 빼면 기록상 실패는 635건 중 0건이다.** 다만 이 값만 내세우지 않는다 — 날짜 칸이 없던 초기 기록의 실패 13건과 **기록 자체가 없는 자동방송 7회**가 따로 있다(§④-2).

> **처음에 통째로 세어 「5.5% 실패」가 나왔다. 그 숫자는 틀렸다.** 실패로 적힌 것이
> **전부 `경보` 행**이었다 — 경보는 방송이 아니라 **시스템이 사람에게 건 말**인데
> `success = 0` 으로 적힌다. 갈라 세지 않으면 *"방송 스무 건에 한 번꼴로 실패"* 로 읽힌다.

### ② 경보 37건 — **하나씩 짝을 지어 보니 셋으로 갈린다** `[실측]`

이 항목이 이번 측정에서 가장 중요하다. 그냥 세면 **「현장 방송 누락 37건」**이라고
적게 되는데, 그건 사실이 아니다. **그런데 반대로 「37건 전부 오경보」도 사실이 아니다** —
처음에 그렇게 적었다가 되물렸다(아래 「어떻게 틀렸었나」).

| 무엇 | 건수 |
|---|---|
| 경보 전체 | **37** |
| 그중 `[방송누락]` 이 **아닌 것** — `[자동업데이트]` 실패(09-08 13:51) | **1** |
| **경보 뒤에 그 방송이 성공으로 적힌 것** | **34** |
| **성공 기록을 못 찾은 것** — 09-01 아침 종합 방송 · 09-04 저녁 식사 전 방송 | **2** |

**짝짓는 법**: 경보 본문이 이름을 댄 방송(`[방송누락] 아침 종합 방송(07:50)…`)이
**같은 날 · 그 경보 시각 이후**에 `자동` + `success=1` 로 적혔는지 본다.
**이름은 정확히 맞춘다** — 처음에 `저녁` 으로 느슨하게 맞췄다가 「저녁 식사 전 방송」
경보가 **「저녁기도」의 성공 기록과 짝지어져** 35건이 나왔다(진짜는 34건).
이름이 서로 포함 관계인 곳에서 `LIKE` 를 쓰면 이렇게 된다.
`scripts/measure-field.cjs` §5 가 그대로 돈다.

> **「성공 기록을 못 찾았다」를 「안 나갔다」로 쓰지 않는다.** 기록이 없는 것과 방송이
> 안 나간 것은 다르다. 09-01 은 그날 첫 기록이 **09:05** 라 07:50 에는 시스템이 안 돌고
> 있었을 가능성이 크다 — 그렇다면 방송도 안 나갔겠지만 **그것도 추정이다.**

#### 어떻게 틀렸었나 — 날짜별 건수만 맞춰 봤다

처음 판은 *"경보가 난 날마다 자동방송 5종이 전부 성공했다"* 를 근거로 **37건 전부
오경보**라고 적었다. **그건 근거가 안 된다** — 09-01 은 경보 3·성공 4, 09-04 는
경보 5·성공 4 라 **수가 맞지도 않았고**, 맞았더라도 **어느 경보가 어느 방송과 짝인지**
모르는 셈이다. 외부 검수가 짚었다.

2026-09-07 하루를 펴 보면 **그날의** 모양은 분명하다:

```
07:55  경보  [방송누락] 아침 종합 방송(07:50)이 나가지 않았습니다
08:01  자동  아침기도 방송                       ← 성공으로 기록
09:05  경보  [방송누락] 국민체조(09:00)이 나가지 않았습니다
09:05  자동  국민체조 방송                        ← 같은 분에 성공
…      다섯 건 모두 같은 모양
```

**감시 장치가 「완료」만 보고 있어서**, 5분 유예를 넘기는 방송
(저녁기도 5.6분 · 아침 투약 안내 대기 6분)이 누락으로 찍혔다.
그래서 판정 근거를 **「시작」과 「완료」 둘**로 갈랐다(`CLAUDE.md` 「누락 감시」 절).

**마지막 경보는 2026-09-08 이고, 그 뒤 자동방송 28건이 성공했으며 경보는 0건이다.**

> **그 34건도 「오경보로 확정」이라고 쓰지 않는다.** 성공 기록은 *"우리 쪽 절차가 끝났다"*
> 이지 *"소리가 났다"* 가 아니다 — §3 ①에서 적은 구분과 **같은 구분**이다. 한쪽에서만
> 엄격하면 그건 기준이 아니라 편의다. 말할 수 있는 것은
> **「그 경보가 틀렸다고 볼 근거가 있다」** 까지다.
>
> **그래서 「누락을 없앴다」가 아니라 「거짓 경보를 줄였다」이다.** 시스템이 거짓말을 하면
> 사람은 곧 아무 알림도 안 믿는다 — 그쪽이 더 비싸다.
>
> **이 숫자를 두 번 고쳤다: 37 → 35 → 34. 둘 다 내가 과장한 쪽이었다.**
> 한 번은 근거가 안 되는 셈법이었고, 한 번은 이름을 느슨하게 맞춘 버그였다.
> **둘 다 외부 검수가 잡았다** — 내 쪽에서는 두 번 다 "됐다"고 보고 넘어갔다.
